# SwampOS — repository instructions for Codex

## Mission and current baseline
- Independent bare-metal x86_64 OS with its own C/assembly kernel and UEFI loader, not a Linux distribution. Preserve the existing implementation and architecture; do not restart from scratch.
- Current source checkpoint: `0.20.0-dev.38` (THE SWAMP AWAKENS). Farkuad 0.13.1 is the user-confirmed VirtualBox fallback. Build 36 validates the retained scene and cursor in QEMU/OVMF. Build 37 drives a USB keyboard and mouse in one opt-in Q35/VT-d guest. Build 38 persists one VFS file through native AHCI and NVMe on disposable Q35 disks. Next milestone is SwampGuard and user processes. VirtualBox display sign-off remains open. Target 0.20.0, longer-term stable 1.0.0.
- Read `CODEX-HANDOFF.md`, `KNOWN-BUGS.md`, `ROADMAP.md`, `BUILD-HISTORY.md`, existing `HANDOFF.md`, `FEATURES.md`, `MISSING.md`, `TEST-REPORT.md`, `README.md`, and relevant source before editing. The repository and real test evidence take precedence over old conversational claims. Treat roadmap as proposed, not implemented.

## Engineering workflow
- Work in large integrated checkpoints, combining related components. No artificial build count, no separate build for each tiny module, and no intermediate approval requests for normal implementation steps. Continue as far as the actual task/session permits; save a resumable state when blocked.
- Keep all existing source, documentation and historical logs; do not silently delete, replace or regress features. Generated intermediates may be cleaned locally but preserve distributed logs and previously required deliverables. Compare manifests to previous checkpoint and original Farkuad. If unavoidable changes/removals are needed, document them and obtain approval for destructive actions.
- Implement production paths, not empty modules or mock-only functionality presented as operational. Make actual test evidence distinguish compile, host/model, guest, and physical hardware results. Never claim tests were run if they were not. Fix failures and rerun. Use existing build scripts; inspect Makefile for exact targets and prerequisites. Record commands, exit codes, hashes and blockers.
- Prioritize real QEMU/OVMF guest validation in a disposable VM; use actual framebuffer and input tests where possible. Do not treat absence of an emulator as a pass. Physical hardware validation is separate. Keep Live boot read-only on physical storage; no destructive disk tests outside explicitly authorized disposable images. Preserve protected boot path and verify changes/hashes explicitly. Do not enable uncontrolled DMA, touch production hardware or weaken security to pass tests.
- Deliver each checkpoint as full cumulative ZIP with hybrid x64 UEFI Live ISO (not raw IMG as primary), SHA-256, component-size report, English styled README, RELEASE, CHANGELOG, FEATURES, MISSING, DIFF-REPORT, TEST-REPORT, TREE and updated HANDOFF; preserve historical logs. Do not artificially pad the ISO. Keep Git LFS for large binaries; no forced push, no credentials in repo, no unsolicited publication. End reports with Git commit commands. Prefer a dedicated branch and PR when using GitHub.
- Style: SWAMP MATRIX // SWAMP OS; soft dark green hacker aesthetic, monospace, ASCII Shrek and exact motto `ITS YOUR SWAMP - ITS YOUR LIFE`; 10-second boot menu. English project docs, Russian concise senior-engineer progress updates, code over prose. State decisions, uncertainties and blockers.

## Original scope (not current claims)
Own kernel; separate per-app default-deny sandbox with user-controlled Internet/LAN/USB/GPU/files/IPC and other permissions; native `.swp`; DEB/RPM/Windows EXE compatibility layers; system VPN including INCY/HAPP-style integration and VLESS/Hysteria2 support, vetted public config discovery; open-source drivers; multiboot and authenticated/encrypted registry; CUDA/ROCm/oneAPI exploration; EXT4 on encrypted block storage, separate verified preboot SwampLogin and authenticated unlock (symmetric disk encryption with RSA wrapping as appropriate); Desktop/Defence/Developer/Privacy/Full editions. Verify feasibility, licensing, trust chain and threat model instead of claiming compatibility from parsers or inventing cryptography. Preserve goals unless user explicitly changes scope.
